# TaskFlow 自動確認・自動アーカイブの実行準備

実装場所は `bde4/taskflow`。本書は準備用で、公開・実サービスへの実行は行っていません。

## 動く経路

- タスク詳細で、本人が自分のGmail／自分のコメントと、対象・期間・対象者・完了条件を一度指定する。代理購入も対象者ごとの個別タスクへ照合する。
- 画面内では既存の認証から `POST /api/task-automation` を呼ぶ。開いている間は15分間隔。明示された許可がないタスクは変更しない。
- 不在時は `scripts/run-task-automation-job.mjs` が、秘密鍵で保護した `POST /api/jobs/task-automation` と `POST /api/jobs/task-auto-archive` をそれぞれ呼ぶ。自動確認は20ユーザーごと、自動アーカイブは20プロジェクトごとの独立したカーソルを最後までたどる。HTTPの単発呼び出しだけでは次のページを処理しないので、定期実行はこのスクリプトを使用する。
- どちらも同じ取得・権限確認・トランザクションを使う。Gmailは既存の選択ラベル／7日／各ラベル20通／本文抜粋の範囲。メール送信・既読化はしない。
- Task、既存の `activityLogs`、`notifications` と、本人の既存 `users/{uid}/secretary` 内の専用文書を使う。別DBや外部キューは不要。

## 完了タスクの自動アーカイブ

全プロジェクトに適用する共有設定を保存して有効にした場合にだけ、完了から指定日数を経過したタスクを対象にする。1日は完了日時から24時間で、AI・Google連携の設定や応答には依存しない。未保存・OFF・設定を確認できない場合にはタスクへ書き込まない。従来の `taskflow.autoArchivePreview.v1` にあるブラウザ限定の期間や初期30日表示は、自動実行の許可として使用しない。

アーカイブは設定の保存後と、1日1回、日本時間0時に確認する。画面を閉じていた／非表示だった場合は、次に開いた時に当日の未実施分を1回だけ確認し、過去日をまとめて再実行しない。共通workerの15分間隔は自動確認用として維持し、アーカイブ側は最初の呼出しで当日の未実施分だけを処理する。

ブラウザと不在時jobは同じ処理を使う。実行直前のトランザクションで共有設定・プロジェクト権限を再確認し、`projects/{projectId}/settings/autoArchiveRun` の日本時間の日付と許可設定の版を照合する。同日・同じ版で実施済みならタスク取得や履歴保存を繰り返さない。未実施の場合はタスクの完了状態と関係を再確認し、アーカイブ・履歴・実施記録を同時に保存する。対象0件も実施済みに含むため、複数タブ・再読込・jobが重なっても一度となる。設定の再保存は新しい版として同日でも一度確認する。取得・通信・commitの失敗は実施済みにせず再開時に再試行し、件数上限や権限失効は設定画面に停止理由を残す。

未完了、アーカイブ済み、中止、完了日不明のタスクは対象外。残す仕事が必要とする親・子・依存先・明示的な全員完了条件も保護する。自動アーカイブ時に `autoArchiveCompletedAt` を残し、人が復元したタスクを同じ完了日時のまま繰り返し自動アーカイブしない。再度未完了に戻して完了した場合は、新しい完了日時から期間を数える。

既存の自動確認workerは `users/{uid}/secretary/task-automation`、アーカイブworkerは `projects/{projectId}` のカーソルを使い、互いのページングや集計を混在させない。各workerは最大100ページを走査し、途中で上限・通信失敗・不正な応答に遭遇した場合は完了扱いにしない。スクリプトは両workerの終了を待ち、片方が失敗しても他方は最後まで実行する。

## 自動更新の照合範囲

曖昧な文章を完了としないため、明確な状態表現を決定的に照合する。商品／イベントと期間が一致し、対象者と結果が同じ文節に明記された根拠を対象にする。質問・予定・未確認・別人の結果・未取得は完了にしない。文章の意味を無制限に推測するAI判定ではない。

申込受付・登録完了・注文成立・支払／購入完了・発送・到着予定・受取・取消・返金を区別。購入は支払／購入完了だけ、登録は登録完了だけ、受取は受取／配達完了だけで完了する。到着予定は明記された年月日をタスクの日付へ反映する。本文抜粋に対象者や年月日がないものは未確認に残る。

Gmailが部分取得・失敗・古い情報の場合、相反する最新連絡を見落としている可能性があるため新規の自動反映を見送る。前の確定結果は残す。設定変更・担当変更・他者編集が入れば、今の内容で任せ直すまで自動更新を停止する。取消時も、人の後続編集を上書きしない。

## 公開時に必要な設定（未実行）

1. アプリとFirestore Rules／Indexesを通常の公開手順で反映する。新しいTaskの自動確認フィールドはクライアント直書きを禁止。履歴のタスク指定複合インデックスと、secretary.automationEnabledのcollection-group単一フィールドインデックスが必要。準備済みの `firestore.rules`／`firestore.indexes.json` を使用する。
2. Secret Managerへ32文字以上のランダムな `TASK_AUTOMATION_JOB_SECRET` を用意し、App Hostingの実行時とCloud Run Jobの双方へ同じ値を渡す。自動確認・アーカイブの両job routeでこの鍵を使う。ログ・Git・SchedulerのURLに値を書かない。アプリ側は秘密鍵が未設定なら503、違う鍵なら401。
3. `ops/task-automation/Dockerfile` をリポジトリルートをcontextとしてビルドし、承認されたArtifact Registryへ公開する。このコンテナはNodeの標準機能だけで動き、メール本文やGoogleトークンを保持しない。
4. Cloud Run Jobへ上記イメージを設定。環境変数 `TASK_AUTOMATION_URL` は公開済みTaskFlowのHTTPS origin、秘密変数 `TASK_AUTOMATION_JOB_SECRET` はSecret Manager参照。タスク数1、並列数1、タイムアウトは運用する人数に合わせる。Jobの実行サービスアカウントはこの秘密へのアクセスだけを与える（Firestore／Gmail権限はアプリ側の既存経路）。
5. Cloud Schedulerから15分間隔（`*/15 * * * *`、`Asia/Tokyo`）でCloud Run Jobを実行。自動確認は毎回、アーカイブは日本時間0時以降の当日未実施分だけを処理する。Scheduler用サービスアカウントへ対象Jobの `roles/run.invoker`、Google API宛のOAuthトークンを設定する。操作対象は製品のJobで、Codexの自動化ではない。
6. 隔離用DB／本人が許可したテストメールで自動確認を、隔離用の完了タスクと共有期間設定でアーカイブを確認してから、App Hosting側 `TASK_AUTOMATION_SCHEDULED=true` を設定する。両機能で同じ表示フラグを使う。この表示フラグだけではJobは作られず、自動アーカイブも有効にならない。

Cloud Run Jobの作成とシークレット設定は[公式CLI](https://docs.cloud.google.com/sdk/gcloud/reference/run/jobs/create)、定期実行の認証設定は[公式手順](https://docs.cloud.google.com/run/docs/execute/jobs-on-schedule)に従う。上記コンテナはページングを含む専用の実行準備であり、現在の環境にJob・Scheduler・Secretを作成したものではない。

## 確認と停止

- ログは `automation: { checked, failed }` と `autoArchive: { checked, archived, failed }`、全体の `failed` 真偽値。`checked` / `failed` は前者がユーザー件数、後者がプロジェクト件数、`archived` はタスク件数。worker自体が失敗した側は `null` とし、成功したように0件とは表示しない。どちらかに失敗があればJobは非0終了し、運用者の既存監視で確認できる。根拠の本文・ユーザーID・秘密鍵・サーバー内部の例外をログへ出さない。
- 再実行は根拠ID／版とタスクの現在版を照合し、重複反映しない。全員条件の成立、取消、期限変更、スヌーズは既存通知の同じIDへ反映する。
- 停止はSchedulerを停止し、必要なら各タスクの許可を解除する。自動アーカイブを止める場合は共有設定をOFFにして、ブラウザ経由の実行も止める。アプリを前の版へ戻してもDB上の完了・日付・アーカイブは戻らない。自動確認の変更は個別の履歴から「反映を戻す」を使い、後続編集があれば手動確認へ戻す。アーカイブは既存のアーカイブ一覧から復元する。
- 最終確認ではPC／390px、会議→整理採用→個別購入→全員条件→取消→期限前案内→Neo→履歴を架空の同一案件で通す。実AI文章品質、実Gmailの到達・認可、本番Indexの有効化と不在時実行は公開後の別検証。
