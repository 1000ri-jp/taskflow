# TaskFlow 総合機能・UI/UX検証レポート

検証日：2026-09-04（JST）  
対象：`/Users/kozue/taskflow-readonly-ui`、`http://localhost:3002`、既存TaskFlow/Firebaseの読み取りデータ

## 結論

TaskFlowの中心設計は、

`タスク → コメント → 確認依頼（共有子タスク） → ダッシュボードのCK表示`

という流れにまとまり、以前より「何を確認し、次にどこを開くか」が明確になっています。計画リスト・テーブル・カレンダーも同じタスクデータを読む表示層として整理され、受信箱と確認待ちの表示内容も揃っています。

ただし、現状をそのまま外部利用・本番展開できる状態とは判定しません。最優先で次の2点を確認・修正する必要があります。

1. 設定画面のアーカイブ済みタスク取得が、Firestoreの複合インデックス不足で失敗する。
2. Firestore/Storageルールに、メンバー追加・通知作成・プロジェクトファイルへのアクセスを広く許可している箇所がある。

この2点を解消したうえで、ダッシュボードの情報源表示、目標の達成条件、増加時の読み取り量を詰めるのが安全です。

## 検証の状態

| 区分 | 意味 |
| --- | --- |
| 確認済み | コード、テスト、またはlocalhost実画面で確認できたもの |
| ローカル限定 | ブラウザ保存・固定データ・プレビューであり、全員には共有されないもの |
| 未確認 | 実ユーザー間、Firebaseルールエミュレータ、本番環境、別端末で未検証のもの |

## 現状評価

### 1. タスクと表示ビュー：概ね良好・確認済み

- カンバン、計画リスト、テーブル、カレンダーは同じ既存タスクを表示する。
- タスク名から従来の詳細モーダルを開ける。
- URLの `?view=`、ブラウザに保存した主表示、初期値の優先順位が定義されている。
- 計画リストでは、親タスクの下に共有確認依頼の子タスクが表示される。
- カレンダーは開催日を推測せず、実際の開始日・期限だけを使う。
- アーカイブ済みタスクを通常ビューから除外する設計は妥当。

実画面では、テーブル・カレンダー・計画リストの切替、期限順、検索保持、親子表示、詳細モーダルを確認できました。表示切替とソートは表示専用で、共有データを書き換えない設計です。

### 2. コメントと確認依頼：設計の軸が明確・一部未確認

「メンバーに通知」と「確認依頼」をコメント投稿欄に集約し、確認依頼は現在のタスクに共有子タスクを1件作る設計です。複数担当者でも完了状態を共有し、親タスクとは別管理になっています。

親から子、子から親・元コメントへ戻れるため、確認依頼が単なるラベルではなく、実際の作業単位として追跡できます。ダッシュボードでは `CK`、黄色背景の「確認待ち」として表示され、受信箱と同じ本文・投稿者・プロジェクト・大タスク・時刻を表示する方向も一貫しています。

確認依頼、子タスク、通知、活動ログをトランザクションで保存するコードとテストはあります。一方、実メンバーへの投稿、別ユーザーでの受信、ルールエミュレータ、本番環境での成功は未確認です。

### 3. ダッシュボード分類：現在の判定は説明可能・文言は改善余地あり

現在の主な判定は次の通りです。

| 表示 | 現在の判定 |
| --- | --- |
| 今日やる | 現在のユーザーが担当する、未完了・中止前・未アーカイブで、期限が今日まで。期限超過も含む |
| 3日動いていない | 未完了・中止前・未アーカイブで、更新日から3暦日以上。期限対象・確認待ちは除外 |
| 要整理 | 担当者または期限が未設定で、期限対象・停滞・確認待ちではないもの |
| 確認待ち | `review_request` の子タスク、または確認依頼通知 |

したがって、更新直後で担当者・期限がないタスクは「要整理」、3日以上更新がないものは「3日動いていない」に分かれます。確認待ちを停滞扱いしない点も、ユーザーが提示した意図に合っています。「今日やる」は自分が担当するタスクだけを表示するため、他人担当・未担当の期限タスクはここには混ざりません。

改善するなら、次の2つです。

- 「今日やる」の中で、今日が期限のものと期限超過を小さく分ける。
- 「3日動いていない」が0件ではなく「表示設定で全件非表示」の場合を、別の空状態として表示する。

### 4. 目標達成と別プロジェクト連携：機能はあるが、意味づけが未完成

「ココナラモニター獲得 0/3」のような目標を作り、人数枠ごとに別プロジェクトのタスクを1件ずつ紐づけられます。リンク先タスクの完了状態を読んで `1/3` を計算するため、ユーザーの「注文を受けたら別プロジェクトで管理し、3人の達成に紐づけたい」という用途には対応しています。

ただし、設定できる「応募」「注文受付」「鑑定開始」「鑑定書完成」「納品」などの達成条件は、現在は表示ラベルとして保存されるだけで、条件ごとに異なるイベントを検出していません。実際のカウントは、選択したタスクの `isCompleted` だけです。

そのため、現仕様では次のどちらかに寄せるべきです。

- すぐ使うなら、表示を「達成条件を表すタスク」に統一し、タスク完了を手動で達成記録とする。
- 本格化するなら、注文受付・納品などをイベントまたは専用状態として定義し、条件ごとに検証する。

### 5. 外部データとサンプル：境界は示されているが、スコアだけ要対処

Googleカレンダーは未接続・読み取り専用、Gmailは表示サンプル、Google Chatは未接続、朝会提案は固定下書き・TaskFlow未反映と明示されています。この表示は安全です。

一方、「今週のスコア」は売上、レビュー、動いているお金などの値が固定データであるのに、画面上で他のサンプル表示ほど明確に「表示サンプル」と示されていません。実データと誤認しやすいため、以下のいずれかが必要です。

- 未接続の間はセクションを非表示にする。
- ヘッダーに常時「サンプル」「未連携」を表示する。
- データソースと更新日時を表示し、実データ接続後だけ数値を出す。

### 6. UI/UX：方向性は良いが、優先順位と情報量をもう一段整理できる

良い点は、状態ごとの色と短い識別子が揃ってきたことです。特に `CK` の黄色表示は、TaskFlowの通常タスクと確認待ちを見分けるのに有効です。タスクの担当者や期限を項目名の後ろに1行で置く方向も、計画リストの密度に合っています。

改善候補は次の通りです。

- ダッシュボードの順序を「返信が必要 → 確認が必要 → 今日やる → 整理 → 停滞」に固定し、行動優先度を説明文でも補う。
- 「担当未定」「期限未設定」は同じ列に詰めず、左に少し余白を置いた補助バッジとして扱う。
- 担当者名の取得中に、長時間「読み込み中」「名前未取得」が残らないよう、キャッシュ・再試行・取得失敗の表示を分ける。
- テーブル／カレンダーは狭い画面で横スクロールになるため、実機幅での確認を追加する。コード上の逃げ道はあるが、実画面でのレスポンシブ確認は未完了。

## 要対処事項（優先順位）

### P0：外部利用前に止めるべきもの

#### P0-1 Firestoreのアーカイブ用インデックス不足

現在のコードは、アーカイブ済みタスクを次の条件で購読しています。

```ts
where('isArchived', '==', true),
orderBy('archivedAt', 'desc')
```

しかし `firestore.indexes.json` に `tasks` の複合インデックスがありません。localhostの設定画面で、実際にFirestoreの `failed-precondition / The query requires an index` を再現しました。設定画面のアーカイブ一覧・復元導線が正常に機能しない状態です。

対応は、インデックス定義を現在のクエリと一致させ、Firebaseの検証環境で適用・確認することです。Firebaseへの反映は未承認のため、この監査では行っていません。

#### P0-2 プロジェクトメンバー権限の見直し

ルール上、`projects/{projectId}/members/{memberId}` への書き込みが、プロジェクトメンバーではなく許可ドメインのユーザーだけで許可されています。プロジェクトへのアクセス判定がこのメンバードキュメントを参照するため、意図しないユーザー追加からアクセス範囲が広がる可能性があります。

Storageでも、`projects/{projectId}/...` の読み書きがプロジェクト所属確認なしに許可されています。会社ドメイン内の別ユーザーが他プロジェクトの添付・画像を読める／変更できる想定なのか、明示的に決める必要があります。

### P1：次の実装サイクルで直すもの

1. ダッシュボードの「今週のスコア」に、サンプル／未連携を明示する。
2. 目標の達成条件を「完了タスクによる手動記録」として整理するか、注文・納品イベントの実装に進むか決める。
3. `useMyTasks` がプロジェクトごとにタスク全体を購読し、コメント受信箱もタスクごとに直近コメントを読み込む構成を見直す。プロジェクト・タスクが増えた場合の読み取り量と初期表示時間を計測する。
4. 「3日動いていない」の対象件数、非表示件数、フィルター理由を表示する。
5. 担当者ディレクトリをキャッシュし、読み込み中・名前取得失敗・プロフィール未登録を別表示にする。
6. 実画面で出ている `DialogContent` の `aria-describedby` 警告を、説明文の追加または適切な関連付けで解消する。
7. 通知作成・ユーザードキュメント作成のルールも、送信者本人・対象ユーザー・サーバー生成値を検証する形に狭める。

### P2：仕上げ・保守

1. FirestoreのIndexedDB persistence APIの非推奨警告を新しいcache設定へ移行する。
2. above-the-foldの添付画像に必要なLCP設定を追加する。
3. iPhone相当幅、横向き、長いタスク名、担当者3名、期限なし、エラー復帰をPlaywrightまたは実ブラウザで確認する。

テストfixture型エラー5件は2026-09-04の引き継ぎ検証で解消し、TypeScript全体検査は通過した。

## 推奨する実装計画

### Phase A：信頼性・権限ゲート

- `tasks` 複合インデックスをコードのクエリと照合。
- Firestore Rules Emulatorで、管理者・メンバー・非メンバー・許可ドメイン外を分けてテスト。
- Storageのプロジェクト単位の読取・書込を同じ権限モデルにする。
- このPhaseが通るまで、実ユーザーへの共有確認依頼を増やさない。

### Phase B：ダッシュボードの行動設計

- CK／返信／期限／停滞／要整理の優先順位を固定。
- すべてのカードに「情報源」「更新日時」「開いた後の行動」を揃える。
- サンプル・未接続・部分取得・取得失敗を同じ表記ルールで出す。
- 3日判定は現在の「更新から3暦日以上」を維持し、空状態だけ改善する。

### Phase C：目標・確認依頼のドメイン確定

- 目標を「完了タスクの手動カウント」として使うのか、イベント駆動にするのか決定。
- イベント駆動にする場合は、注文受付・鑑定開始・完成・納品の状態、証跡、重複防止、取消・訂正を設計。
- 確認依頼は、依頼中・回答済み・差し戻し・期限超過の状態を必要に応じて分ける。

### Phase D：連携・スケール

- コメント受信箱とマイタスクをサーバー集約または段階取得にする。
- Google Calendar、Gmail、Google Chatは、それぞれ接続状態・権限・取得時刻・失敗時導線を揃える。
- 実ユーザー2名以上・複数端末・低速通信・大規模プロジェクトで確認する。
