# 朝会提案のローカル試作

対象は `http://localhost:3002/my-dashboard` の「今日の朝会から」。ユーザーの差し替え添付を整理した固定データ（`meeting-memo-v2.ts`）を使う。会議日は2026/9/2と記載される一方、録音日時は2026/9/3 08:58 JST。日付は未確定のまま保持する。原音声・原文字起こしや公式規約は未検証。実行時の会議取込・LLM呼び出し・自動更新は未接続。

## 表示と照合

- 4親タスクの下に35件の実行候補と1件の検討候補。添付の36項目から、親4-1と親4-2の表示設計を1件に統合し、登録ルールに従って会議日・募集実施日の確認タスクを1件追加。元の36項目への参照はすべて保持する。
- 通常は13のチェックリスト案を折りたたんで表示する。元メモの4分類と35提案のID・担当・期限・完了条件・依存関係を保持する。分類と追加先の実タスクを区別し、指定した大タスクの下に子タスクをまとめる試作である。実データの親子関係は変更しない。
- 詳細にタイトル、担当、期限・時期条件、優先度、作業ステータス、内容、完了条件、依存タスク・前提、元メモを表示。親1-7は親1-2〜6、親2-8は親2-2〜5に依存する。新たな依存関係を勝手に追加しない。
- ユーザーの追加指定に従い「各自」は会議参加者3名（Naofumi Higashikawauchi・こずえ・脊古香織）へ展開する。登録先候補プロジェクトのメンバーを読み取り専用で取得し、名前・別表記が一意に一致した場合だけIDを照合する。複数担当はチェックボックスで変更でき、同名・未取得は推測しない。「実装担当」「3名」や未指定の担当を個人名に補完しない。優先度・作業ステータスの未指定も保持する。
- 「今日21時」「13日まで」「14日朝9時」は絶対日付に変換しない。「提出前」「資材到着後」は条件のまま保持する。全候補の初期dueDateは空欄。確認待ち12項目を独立した欄に掲載する。
- 親4-7は検討候補専用欄。採用・編集などの実行候補操作を提供せず、ストアでも操作を拒否する。コア表示改善が終わるまで実装しない。
- 読み込んだ参加プロジェクトのタスクに対して題名／別表記で保守的に照合する。プロジェクト名も候補であり、登録先確定ではない。複数候補、完了・中止済み、プロジェクト未一致、元の未確定事項は要確認にする。
- 読み込み中・取得失敗・サンプルモードでは照合待ち。取得失敗を新規と判定しない。別題名の重複を完全に検出する仕組みではない。変更不要であることも自動断定しない。
- 「登録済みタスクを含む」「新規候補」「照合待ち」に分け、混在するまとまりは子タスクの内訳を表示する。未指定の担当や期限に関する要確認と、登録状況の分類は区別する。
- 詳細は登録済みの件名・担当・期限・優先度と提案を横並びで比較する。対応先を人が確認する、新規として扱う、別の既存タスクを検索する操作を提供する。対応先が削除・アーカイブ・参加範囲外になった場合は照合待ちに戻す。認証情報の混入を避けるため、既存説明本文は表示しない。タイトルの既知の認証情報パターンは伏せる。手修正や保存復元でもパスワード・トークン等の既知パターンを拒否する（万能の機密検出ではない）。
- 複数のモニター提案が同じ既存タスクに一致しても上書き・統合しない。親の目的と実行単位の確認は必要。
- 旧版の9/13・9/14の確定日、動画URLは空欄可、LINEスタンプ項目、完了済みの判断を持ち込まない。新版の「確認が終わるまで出品しない」を保持する。東京ゲームショウへの関連づけは旧版からの推測ではなく、後のユーザー明示補足による。

## 大タスク → チェックリスト → 子タスク

- ユーザーの追加指定で、出展情報の準備・提出（ex-submit）は「東京ゲームダンジョン」、参加登録・チケット購入（ex-attend）は「東京ゲームショウ」を追加先候補にする。参照可能な実タスクから名前を照合し、一意の場合だけ候補として表示する。同名複数・未取得・削除・アーカイブ・参照範囲外では確定せず、選び直せる。
- 2026/9/3の実画面では「イベント / 東京ゲームダンジョン」と「気になる展示会 / 東京ゲームショウ2026」を候補として確認した。IDは固定せず毎回取得データから照合する。
- 他のまとまりにはイベント名・追加先を自動で補完しない。「追加先を設定」で参照可能な大タスクを検索し、チェックリスト名と合わせてブラウザ下書きに保存できる。完了・中止済みの追加先は警告し、再開しない。
- 子タスクの作業完了チェックはレビューの採用・保留と別状態。一般の子タスクは既存の下書き編集で担当・期限を持つ。チェック欄から期限を変更しても同じレビュー下書きに反映される。
- 「各自」のEX-9は担当者別の購入チェック・個人期限に展開する。3名の場合は3項目になる。通常の34提案と合わせて作業チェックは37項目、原典の提案は35件のまま。表示名の別表記は同じ個人キーとして扱い、担当が変わっても他人の完了状態へ転用しない。担当未指定なら個人チェックを生成しない。
- 作業チェック・個人期限・追加先は `taskflow.meetingChecklistDraft.v1` に保存する。既存の `taskflow.meetingProposalReview.v2` のレビュー・重複照合先とは別。チェック欄の「元に戻す」はそのテスト入力だけを解除し、追加先解除はチェック結果やレビューを消さない。
- 追加先が「イベント」のタスクで、重複する既存作業が「展示会出展」にある場合も、それらを移動・複製・統合しない。実反映時には人による差分確認が必要。

### 将来の実データ反映に必要な変更（未実装）

現在の `ChecklistItem` は本文・完了状態・順序のみ。担当・期限を実タスク内でも使うには、既存項目を壊さない任意フィールドとして担当ID配列・期限等を追加し、Firestore保存、読取、詳細画面、マイタスク抽出を対応させる必要がある。DB変更案のレビュー、認証、権限、既存データ互換、重複防止と実行承認を経てから実反映する。本試作では型やFirestoreのスキーマは変更していない。

## 保存範囲

`taskflow.meetingProposalReview.v2` に会議バージョン `meeting-date-unconfirmed-v2` と提案ID別の確認状態・ユーザー修正・対応先・照合済み複数担当IDを保存する。既存のv2レビューを保持し、新しい任意フィールドがないデータも読み込める。旧版の `taskflow.meetingProposalReview.v1` は変更しない。保存先はこのブラウザであり、ユーザー別／全員共通保存ではない。他の端末には同期されない。

「採用」「保留」「不要」は下書きレビューの印。「直す」は件名・複数担当・期限・提案内容で、編集・対応先変更は未確認へ戻る。採用時には展開済みの担当名と、一意に照合できた場合の担当IDを下書きへ保存する。元のメモ・未解決事項は残す。「未確認に戻す」は編集・対応先を保持し、「元の下書きに戻す」はその提案の編集・対応先・レビューだけを解除する。ブラウザ保存失敗時は警告し、メモリ上の変更だけを維持する。

**Firestore・タスクAPI・AI tool executorへの書き込み経路はない。採用はTaskFlowへの新規作成・更新・完了、メッセージ送信、購入、認証変更、DB変更やPR作成を意味しない。** 現在の会社データは変更しない。将来の反映機能には認証、明示的差分確認、更新対象選択、担当ID照合、競合検知、実行承認・重複防止を別途設計する。
